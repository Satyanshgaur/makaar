# Decisions and corrections to docs/research.md

Verified against primary sources on 2026-11-02.

1. **TeleOCR runtimes.** teleocr-rs GGUF is explicitly "Not for llama.cpp". The model card also lists vLLM, SGLang, Transformers, and community GGUFs for Ollama/LM Studio; re-check those in week 1.
2. **IndicOCR** ships as safetensors with a Python/CUDA installer, tested on vLLM. "In-process on ONNX Runtime" is unproven; needs a conversion spike, else sidecar/fast-mode only. It scores 92.76 vs PaddleOCR-VL-1.6's 96.36 on English OmniDocBench v1.6, so it is an Indic-only specialist.
3. **Texo weights** (alephpi/FormulaNet) are tagged AGPL-3.0, not just the web app. Default formula specialist: PP-FormulaNet_plus-S (Apache-2.0). Texo only as an optional download.
4. **PP-DocLayoutV3** has community ONNX exports (Apache-2.0, ~480 ms/page CPU on Apple M). Layout module does not need to fall back to TeleOCR's built-in layout.
5. **PaddleOCR-VL-1.6 GGUF**: an official PaddlePaddle repo exists; the mmproj file is required alongside.
6. **Tectonic** is maintained (0.17.0, MIT).
7. Still unverified: speed estimates, speculative-decoding speedup, GPU prices.
8. Code licence: Apache-2.0 (provisional, doc left MIT vs Apache open).
9. **Dev GPU is an RTX 3050 6 GB laptop**, enough for the 0.9–1.2B engines at Q8 but not vLLM-batched fast-mode numbers. Throughput/cost claims must be measured on rented GPUs, not here.
10. **One adapter for both engines.** `OpenAIEngine` talks to any OpenAI-compatible server (llama-server for PaddleOCR-VL, vLLM for TeleOCR), so Week-1 comparison uses identical scoring code.
11. **TeleOCR (renamed from NaviDC-OCR; HF `StarDoc-AI/TeleOCR`) is a two-step pipeline**, not a whole-page prompt: layout pass ("Analyze the image layout.") then per-region prompts ("Please output the text content from the image.", "...LaTeX format.", OTSL for tables). Official runner is `infer.py` on vLLM with ~200 pinned deps. We score it through `runner --predictions` using its output rather than faking a whole-page prompt, which would understate it.
12. **TeleOCR on llama.cpp** works only with a patched build (nandraj/NaviDC-OCR-GGUF, PATCHES.md); stock llama.cpp fails with `check_tensor_dims`. Q8_0 is 805 MB there, vs ~1.5 GB for teleocr-rs.
13. **Smoke-tested** PaddleOCR-VL-1.6 GGUF on llama-server (CUDA build, RTX 3050 6 GB): ~1.9 GB VRAM, 0.8 s for a short paragraph. Not a gate number; real pages pending.
14. **Tectonic**: `cargo install` needs libpng/harfbuzz dev packages (sudo); the prebuilt musl 0.17.0 binary works. First compile downloads the TeX bundle and is slow.
15. **Layout: official PP-DocLayoutV3 ONNX** (`PaddlePaddle/PP-DocLayoutV3_onnx`, Apache-2.0, 130 MB) runs on the `ort` crate (ONNX Runtime 1.31, telemetry off). Input is the page squashed to 800×800 RGB in 0–1; output rows are `[class, score, x0, y0, x1, y1, reading-order key]` in page pixels, so reading order comes from the model. ~0.9 s/page on CPU (i5-13420H, 6 threads), same as Python onnxruntime.
16. **Layout threshold 0.3, not the model's 0.5.** At 0.5 handwritten pages lose most regions (maths1: 7 vs 23 after dedup). Lower thresholds bring duplicates, so `layout::postprocess` drops same-label IoU > 0.5, any-label IoU > 0.9, same-label boxes nested in a kept one, and inline formulas inside kept text. Eyeballed on the 10 eval pages; calibrate on the test set.
17. **Handwritten prose comes back as one page-sized region** (plain_notes → a single `algorithm` box). That is the whole-page fallback the plan already has; the layout model can't tell handwriting, so `handwriting` blocks need another signal later. The raw label is kept on each block (`label`), since `text` covers code, headers and page numbers.
18. **Per-region recognition beats whole-page on PaddleOCR-VL** (the way it is meant to run). `core::pipeline`: layout → padded crop → task prompt by block type (`OCR:`, `Formula Recognition:`, `Table Recognition:`); figures kept as images. On the 10 eval pages, clean NED mean 0.481 → 0.311, loops 2 → 0; diagram pages 0.83/0.96 → 0.11/0.20; printed3 0.25 → 0.08 (Gemini 0.076). No page got worse.
19. **Messy layouts are read whole.** A non-figure box around ≥2 regions is dropped (it repeats their text), and if the raw layout's overlap score is > 0.1 the page goes to the general model as one block: handwritten pages' text bands overlap, so regions read lines twice or miss prose between formulas. 0.1 splits the eval pages cleanly (diagrams ≤ 0.06, handwritten maths ≥ 0.11); calibrate on the test set.
20. **Loop guard.** Each region's token budget is its page-area share of 4,096 (×1.5, floor 128), so a loop costs seconds. A block that hits it has its repeated tail trimmed and is `flagged` for review.
21. **Gate 1 still fails on this sample.** On the 7 pages Gemini (via `agy`) transcribed: Paddle routed 0.365 vs Gemini 0.281 clean NED; printed pages ~0.15 vs ~0.03. Ground truth is human-written (not Gemini-drafted). Much of the printed gap is formatting the truth adds (constructed tables, display-math choices), not misread text. 10 pages can't decide the gate.
22. **Gate 2 preview, CPU only** (i5-13420H, 6 of 12 threads, llama-server Q8 `-ngl 0`, GPU hidden): median 39 s/page, worst 60 s, server RSS 2.55 GB; scores match the GPU run within noise. Under the 60 s gate on a near-target CPU; the real gate needs the laptops in the test plan. RTX 3050: median ~3.4 s/page.
23. **Gemini API baseline** (PR #9, `scripts/gemini_baseline.sh`): `gemini-3.5-flash` (3.8 Flash was overloaded with 503s, 2.5 Flash is closed to new keys), ~6 s/page. Clean NED on all 10 pages: Gemini 0.277 vs Paddle routed 0.311, a 3.4-point gap against the 3-point gate. By bucket (Gemini/Paddle): diagrams 0.248/0.155, maths 0.362/0.547, printed 0.192/0.151. The whole gap is handwritten maths, which v1 already concedes to Gemini.
24. **Dewarping does nothing for the current eval set.** UVDoc (docuwarp's ONNX, 16 MB, ~0.2 s/page on 4 CPU threads) only trims margins on these flat scans. Keep it for phone photos; measure it when the test set has some.
25. **Reading handwritten maths line by line barely helps.** Splitting pages into ink bands by row projection and reading each with `OCR:` moved the maths mean 0.547 → 0.532 (maths3 got worse); bands of a few lines, 0.542. Close handwritten lines merge into one band and the model reads only part of it. The errors are recognition (Θ → 0, hallucinated chains), so the fix is the v2 fine-tune, not routing.
26. **LaTeX export is compile-checked** (`core::latex`). Prose is escaped and common symbols (→ ≤ ∴ …) mapped, `\(…\)`/`$$…$$` math passes through, code (`algorithm` without math) goes in `verbatim`, tables from HTML or OTSL become `tabular`. Tectonic compiles the whole file; if that fails, each paragraph or block with a command is compiled alone (~0.25 s each) and failures become verbatim source. Those blocks, and paragraphs with unclosed `\(`/`\[`/`$$`, are flagged. All 10 eval pages compile (0.5–3.5 s each); one is flagged (maths1, unclosed `\(`).
27. **Word export writes OOXML directly; no pandoc.** Pandoc is ~150 MB and GPL, too big for a <50 MB installer, and the one LaTeX→MathML crate (`latex2mathml`) was last released in 2020. `core::omml` converts the LaTeX subset notes use (scripts, `\frac`, `\sqrt`, `\left…\right`, accents, `\text`, matrices/cases, ~150 symbols, function names) to native Word equations. Unknown commands are an error, and the math is kept as LaTeX source with the block flagged. `core::docx` writes headings as Word heading styles, code in a Courier New style, tables as Word tables, and figure crops embedded at most 6.5 in wide. Page breaks are `pageBreakBefore` on the next page's first paragraph, since a break paragraph spills onto a blank page when the previous page is full. All 10 eval pages export in 0.01 s with every formula converted. LibreOffice renders the result; Word itself is untested.
28. **`makaar` CLI is the first end-to-end app.** `makaar convert <pages|folders> -o out/` runs ingest → layout → per-region recognition → .md, compile-checked .tex/.pdf, .docx and the document JSON (the review screen's input). Figure regions are saved to `<name>_files/`. Job state (SQLite queue plus one JSON per finished page) lives in `out/.makaar/`, so rerunning the same command resumes: interrupted pages are redone, failed ones retried, and finished ones skipped. Different inputs in the same folder are refused unless you pass `--fresh`. Tested: a run killed with SIGTERM and then SIGKILL mid-page resumed with only the unfinished pages. 3 printed pages take 28–69 s each on 6 CPU threads.
29. **llama-server runs as a sidecar the app owns.** It gets a free localhost port, is ready when `/health` returns 200 (1 s here, since the model is mmapped), and is killed on drop. `--gpu-layers 0` also hides CUDA, because a CUDA build otherwise still reserves GPU memory. Killing `makaar`, even with SIGKILL, left no orphan server in testing. Found via `$MAKAAR_LLAMA_SERVER`, beside the executable (how the installer will ship it), or on PATH.
30. **First-run download is pinned and verified.** `makaar models --download` fetches the three required files from Hugging Face at fixed commits, hashes while streaming to `.part`, and renames only on a SHA-256 match. The hashes are HF's LFS ids, checked against a local file. Startup checks sizes only; `--verify` re-hashes. Models go in `$MAKAAR_MODELS`, `./models` in a checkout, or the per-user data folder.
31. **PP-OCRv6 small is the printed-text specialist** (official ONNX, Apache-2.0, 31 MB, `core::ocr`): DB line detection (axis-aligned boxes; thresholds from the model's `inference.yml`) and CTC recognition over its 18,708-character dictionary. A whole page takes ~1 s on 4 CPU threads. Read whole, it is worse than PaddleOCR-VL per region (printed clean NED 0.18–0.45 vs 0.08–0.28): it loses code layout and math. But its mean character probability separates printed from handwritten (pages 0.97–0.99 vs 0.78–0.88), so it is a specialist behind a confidence check, not a replacement. PP-FormulaNet_plus-S has no official ONNX (only -L), so formulas stay on the general model for now.
32. **Router: prose regions try the specialist and keep its text only at mean confidence ≥ 0.98.** Code (`algorithm`), formulas, tables and the whole-page fallback go straight to the general model. Calibrated offline (`examples/route_sim.rs`) by replaying the stored PaddleOCR-VL pages region by region. Printed regions score 0.986–1.000 and handwritten ones at most 0.971. At ≥ 0.97 the 10-page mean equals pure PaddleOCR-VL (0.311); the only change is printed3 0.080 → 0.086, mostly from reflowed line breaks. Lower thresholds accept handwriting and hurt (0.90 → 0.332). Accepted blocks are `verified`. On CPU, printed3 drops from 69 s to 1.5 s and printed1 from 46 s to 38 s.
33. **The general model starts lazily.** `LazyServer` launches llama-server on the first region that needs it, so a batch the specialist finishes never loads the 1.8 GB model. This is the plan's "load the general model only when needed", short of batching failures across pages. ONNX Runtime allows one environment per process, so layout and OCR share it.
34. **The review screen is a local web page served by the CLI** (`makaar review out/notes.json`), not a Tauri app yet. It shows the scan with block boxes (flagged red, verified green) beside editable block texts with live previews. Math is previewed as MathML from the same LaTeX parser as the Word export, so nothing like KaTeX has to be bundled, and math that won't parse shows in red: what the reviewer sees is what Word will get. "Looks right" clears a flag, edits set `edited`, and saving re-exports every format; the exporters don't re-flag blocks the reviewer edited for unclosed math. It binds 127.0.0.1 only, checks the Host header (DNS rebinding), and requires a per-session token in every request, so other local pages can't read or overwrite the notes. The document and initial previews are inlined into the page, so it renders in one request. Tauri can wrap this page later unchanged. `convert` now records each page's absolute scan path for it.
35. **`makaar setup` installs everything a user needs**: the six model files (`models --download`) plus llama.cpp's official prebuilt release for the platform, pinned to build b12137 (MIT). Each archive is checked against the SHA-256 GitHub publishes for it, then unpacked under the models folder, with paths escaping the folder refused and the executable bit kept. CPU builds are the default because they run everywhere; `--backend vulkan` covers most laptop GPUs, and macOS builds use Metal. Tested on Linux x64: download, checksum and unpack, and the CLI then finds the server. Running the downloaded server itself was not tested here.
36. **Release builds** (`.github/workflows/release.yml`): the CLI for Linux x64/arm64, macOS arm64 and Windows x64, each smoke-tested (`--version`, `models`). On a `v*` tag they are attached to a draft release. ONNX Runtime is linked into the binary by the `ort` crate, so the archive is one executable plus README and LICENSE (installer < 50 MB). A Tauri desktop wrapper around the review page is the remaining installer step.
37. **General-model blocks under 0.9 mean token probability are flagged.** In the eval set PaddleOCR-VL scores handwritten blocks 0.75–0.89 and printed ones 0.91–1.00. The pages this flags average 0.42 clean NED against about 0.15 for the rest. It flags all handwriting, which v1 doesn't claim to read reliably, and routes it to the review screen. Provisional: the plan wants every threshold calibrated on the test set, and the eval harness's `flag_quality` needs block-level truth to do that.
38. **PDF input via hayro** (pure-Rust rasterizer, Apache-2.0/MIT; no pdfium or poppler to ship). A PDF expands to one queue entry per page (`file.pdf#page=N`), each rendered at 2,000 px on the long side (about 240 dpi on A4), scanned or digital. The rendered page is saved in the job folder so the review screen can show it. Tested on the HumynLabs handwritten-notes PDFs: 20 CS pages converted end to end.
39. **`core::app` holds the convert job and exports**, with progress through a callback (`Progress`, serializable), so the CLI and desktop app share one code path. `Review::spawn` runs the review server on a background thread and returns its URL, for the desktop app.
40. **Desktop app: Tauri v2 over the same core** (`desktop/`). The home window handles first-run download with progress, picking images, PDFs or folders (native dialogs, run from Rust so the page needs no file permissions), the output folder, formats and GPU on/off, then converts with live per-page progress. It opens the review screen (`Review::spawn`) in a second window. The UI is one HTML file with no npm toolchain. `makaar-desktop <files…>` prefills the pages, for "Open with". On Linux it sets `WEBKIT_DISABLE_DMABUF_RENDERER=1` unless the user has set it, since WebKitGTK's DMA-BUF path drew garbage in testing (a known issue on NVIDIA and remote displays). Tested under Xvfb: launch, convert 3 pages, open review. Release installers are deb and rpm at 20 MB (under the 50 MB target) and an AppImage at 125 MB (bundles WebKit). macOS (dmg) and Windows (NSIS) bundles are built by the release workflow.
